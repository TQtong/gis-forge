# Bug 复现与修复记录规范

每个修复的 Bug 必须有一份专门的 Markdown 文档，完整保留从问题复现、原因定位到修复和回归验证的过程。该文档是修复交付的一部分，不能用聊天记录、提交标题或一句“已修复”代替。

## 文件组织

- 新记录统一放在 `doc/bug-fixes/`，文件名使用 `YYYY-MM-DD-简短问题描述.md`；日期为记录创建日期，描述应能明确识别问题。
- 一个 Bug 对应一份独立文档；同一 Bug 的补充修复、验证或再次出现，继续更新原文档并注明日期，保留原有复现和修复历史。
- 已有其他目录中的专门记录可以保留；在本目录建立该 Bug 的记录并链接原文，新增过程在本目录持续维护，避免两份文档内容分叉。
- 日志、截图、视频或诊断数据应提供可访问的路径或链接，并说明它们证明了什么；关键复现条件和验证结论必须直接写进 Markdown，不能仅依赖临时产物。

## 每份记录必须包含的内容

### 1. 问题概述

记录问题标题、发现日期、当前状态、影响模块和用户可见影响，分别描述预期行为与实际行为。注明相关 Issue 或原始反馈（如有），说明受影响的模式、场景及范围。

### 2. 复现环境与前置条件

记录修复前的代码版本或提交、启动命令、访问入口、所需数据及配置。根据问题补充操作系统、浏览器版本、GPU/WebGPU 能力、网络状态和缓存条件。

地图与渲染问题还需记录相关的 2D/2.5D/3D 模式、经纬度、zoom、pitch、bearing、视口尺寸、像素比例、图层和数据源；注明单位和数据加载状态，使他人能建立相同条件。

### 3. 复现步骤与证据

用编号步骤写清从启动到触发问题的完整操作顺序、输入数据、参数、等待条件及触发动作，给出每次复现的实际现象和预期结果。偶发问题说明触发频率及观察时长。

附上适用的错误日志、堆栈、截图、视频、测试失败结果或诊断数值。无法复现时明确写出已尝试的条件、缺失信息和限制，不得把猜测写成已复现的事实。

### 4. 定位过程与根因

记录关键排查步骤、观察证据、已排除的原因及最终确认的根因，指出相关文件、函数、数据流或资源生命周期。解释该原因如何导致问题，区分已证实结论与待验证假设。

### 5. 修复过程

按实际执行顺序记录修复方案、关键改动及其原因，说明修改的文件、接口或算法，以及如何覆盖错误和边界条件。对影响最终方案的失败尝试或方案调整，保留原因和结果。

记录必要的兼容性、精度、性能、资源释放和受影响路径处理，说明为什么修复能够消除根因。关联相关测试、已有提交和历史记录；尚未产生的提交哈希可通过该文档的 Git 历史追溯，不得填写虚构哈希。

### 6. 修复验证与回归

按原复现步骤重新操作，记录修复前后的具体差异。列出实际执行的测试或检查命令、测试文件、环境、结果和必要证据，覆盖受影响的相邻功能及适用边界。

涉及 GPU、地形、相机、Shader 或交互时，记录真实渲染与操作结果，不能只以类型检查或构建通过认定修复有效。未执行或受环境阻塞的检查必须注明“未验证”及原因，不能记为通过。

### 7. 结论与后续状态

明确是否已解决、是否通过原场景和相关回归验证，以及仍存在的限制或未完成项。只有完成必要修复与验证后才能标记“已修复并验证”；再次出现时追加新日期、现象和处理过程，保留之前的结论及证据。

## 执行与提交要求

1. 开始修复时先查找已有记录；新 Bug 创建独立文档，先写已知现象、环境和复现信息，再随排查更新。
2. 每个小步修复提交都同步更新该 Bug 文档，记录本次实际完成的改动及验证结果。文档与对应修复代码一起提交，不能等全部代码提交后再凭记忆补写。
3. 文档内容必须具体、真实、可操作；正在调查的未知事项要明确标注，最终交付不得留下空章节、占位说明或缺失的必要验证。
4. 提交前检查复现步骤是否足够执行、根因是否有证据、修复过程是否可追溯、验证结果是否真实，以及文档链接是否可访问。
5. 交付时提供该 Bug 文档路径及相关提交；缺少独立记录或复现、修复、验证过程不完整，视为修复任务未完成。
